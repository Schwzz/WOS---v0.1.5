# Auralis branding, terminal rework, and repository review

Scope: implement the approved visible rename and terminal simplification, then review the repository. Desktop conversion, avatar redesign, speech input, vision, and tools remain future work.

## Implemented

- Visible Auralis branding across terminal messages/help, window/web labels, documentation, workflow name, and the shipped Nexis project identity. Nexis remains the character name.
- Existing storage paths, configuration, character IDs, repository URL, protocol identifiers (`WOS-Overlay`, `X-WOS-Token`), and restart environment variables remain compatible. Both legacy and new system-message prefixes are excluded from speech.
- Original teal/amber terminal palette and warm light theme, compact composer, chat title header, short character/phase/voice status, and quieter footer.
- Sidebar hidden by default; Ctrl+B reveals provider/model information and extra shortcuts.
- No inline scrollable command-output panel. Brief notices expire after eight seconds; Ctrl+L dismisses them. F8 or the Details button opens the latest 500 lines in a separate dialog. Escape/F8 returns to the draft. PageUp/PageDown scroll the active details view.
- Slash completion, command/model/provider/character pickers, voice shortcuts, Markdown, chat drafts, reading position, and the shared session remain supported.

## Review corrections included

The independent review found two introduced regressions, fixed before delivery with regressions observed failing and then passing:

1. Combining old message prefixes initially bypassed the plain terminal's error-color logic. Auralis errors now remain red and ordinary status messages blue.
2. App-level PageUp/PageDown initially bypassed the details dialog. They now scroll the active journal instead of the conversation behind it.

## Existing fixes needed

These findings are outside the two approved implementation items and remain unfixed.

### High: partial save failure can discard an exchange on the next save

Sources: `core/conversation.py:318-340`, `core/session.py:420-436`.

`update_chat` saves the chat file before updating its index. If saving the index fails, Session rolls its in-memory messages back even though the chat file was already changed. A subsequent successful exchange overwrites that file from the rolled-back memory, losing the earlier exchange.

Reproduced with temporary data by making `save_index` raise during `_record_exchange`: memory had zero messages while disk had two. The next successful exchange left disk with only the second exchange.

Suggested fix: define a recoverable commit boundary for chat/index writes, then reconcile the index rather than treating an already-written exchange as absent. Add fault-injection tests at each persistence step.

### High: a corrupt chat index can hide existing chats

Sources: `core/conversation.py:66-89,278-312`.

A malformed/unreadable index is returned as an empty list. Creating a chat then replaces the index with one containing only the new chat. Existing session files survive but disappear from normal listing, selection, and chat-limit counting.

Reproduced by creating two chats, corrupting the index, then creating another: three chat files remained, but only one was indexed.

Suggested fix: preserve the damaged index and rebuild from valid chat files, or block mutations until recovery succeeds. Distinguish missing files from corrupted/unreadable ones.

### Medium: one failed web-history fetch can leave the conversation stale

Sources: `overlay/web/chat.js:238-239,429-432`.

The frontend stores a new `chatVersion` before loading history successfully. If that fetch fails, subsequent healthy state polls see the same version and do not retry. A new revision or reload is needed to recover.

Reproduced in an in-memory version of the JS harness by rejecting a history request after a version increment: the backend had two saved messages while the frontend stayed empty and issued no retry on its next healthy poll.

Suggested fix: commit the rendered history version only on success, or retain a retry flag.

### Medium: native window failures can leave expansion state incorrect

Source: `overlay/main.py:208-225`.

`_expanded` is changed before native resize/move succeeds; exceptions are swallowed. A failed resize can leave the backend reporting expanded, while a repeated request returns early without retrying.

Reproduced by making the native resize method raise: `get_window_state()` still returned `expanded=True`.

Suggested fix: commit state after native success and return a window-control error. The planned normal desktop window should also replace the custom resize path; Windows cursor alignment still needs native validation.

## Improvements worth doing next

- Address the two persistence findings before adding features.
- Then separate the application runtime from `start.py`'s interactive loop for independent Desktop mode.
- Add explicit model-request cancellation and consistent request deadlines; speech stop currently suppresses current/late audio but does not abort model generation.
- Persist terminal theme/sidebar preferences and optionally drafts across restarts.
- Convert the current Companion into the planned normal Desktop app; its floating-window behavior has not changed in this pass.
